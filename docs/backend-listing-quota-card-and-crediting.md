# Лимит объявлений (increase quota): карта не работает + подтвердить зачисление

**Дата:** 2026-09-21
**Кому:** команда бэкенда (`kodo-az/api.wawatair.com`)
**От:** мобильный клиент
**Контекст:** после фикса с `apple_live/google_live=true` и listener'ом на
`ListingApproved` промо (VIP/Boost) применяются. Этот файл — только про
**увеличение лимита объявлений** (`listing-quota`), где остаются два вопроса.

> Оговорка: доступа к свежему клону бэкенда сейчас нет, ссылки — по классам и
> методам из прошлого разбора. Номера строк проверьте у себя.

## 1. ГЛАВНОЕ: оплата лимита картой на проде невозможна

Для промо (VIP/Boost) карта работает через Kapital:
`initCardCheckout` → `payment.checkout_url` → `PaymentCallbackController::kapital`
→ `confirmCardPayment()` (идемпотентно зачисляет).

**У лимита такого пути нет.** `ListingQuotaPurchaseService::pay()` для
`method: card` при `mock_payments=false` кидает `provider_unavailable`. То есть:

```
POST /listing-quota/orders/{id}/pay   { "method": "card", ... }
  → ListingQuotaPurchaseService::pay()
  → mock_payments=false + method=card → throw provider_unavailable   // 4xx
```

Пользователь, выбравший «Bank kartı» для лимита, **никогда не сможет оплатить** —
заказ навсегда `pending_payment`, деньги не списываются, лимит не растёт.

### Что решить (одно из двух)

- **(A) Реализовать карту для лимита** — зеркально промо: `.../pay {method:card}`
  возвращает `payment.checkout_url`, а `PaymentCallbackController` (отдельный
  роут для quota-order по `public_id`) идемпотентно подтверждает оплату и
  вызывает `ListingQuotaPurchaseService::markPaidVia()`. Тогда нужен публичный
  https `APP_URL`/`KAPITAL_RETURN_URL_BASE` (как для промо).
- **(B) Официально отказаться от карты для лимита** — тогда клиент уберёт плитку
  карты и на Android (на iOS её уже нет — см. ниже). Оплата лимита останется
  только через стор (IAP).

**Нужен ваш выбор A или B.** До ответа клиент показывает карту только на
Android; на iOS — нет.

## 2. Подтвердить, что IAP-зачисление лимита работает на проде

В отличие от промо у лимита **нет модерационной задержки** (нет
`pending_activation`): оплаченный заказ должен сразу увеличивать лимит через
`ListingQuotaPurchaseService::markPaidVia()`.

Теперь, когда `apple_live/google_live=true`, стор-покупка лимита должна проходить
по тому же шву, что и промо:

```
POST /listing-quota/orders/{id}/pay   { "method":"apple", "receipt": "<base64>" }
  → RedeemsStorePurchase::redeemStorePurchase
  → IapService::redeem()  (AppleReceiptVerifier, идемпотентно по transaction_id)
  → ListingQuotaPurchaseService::markPaidVia()  → лимит += extra_listings
```

**Проверьте на проде реальной стор-покупкой (Sandbox/TestFlight):**
ответ `/pay` = **HTTP 200 + `data.status:"paid"`**, а `GET /me` сразу отдаёт
увеличенный `listing_quota[<type>].limit`. Если это так — п.2 закрыт, фиче
лимита достаточно стора.

---

## 3. `/me` должен отдавать свежий лимит сразу после `/pay`

Клиент после успешной оплаты **перезапрашивает `/me`** и показывает
подтверждённый «Yeni limit: N → M», а также даёт создать объявление с новым
лимитом.

- Убедитесь, что `GET /me` **не отдаёт закешированный** `listing_quota` — сразу
  после `/pay` там должны быть новые `{limit, remaining}` по нужному типу
  (`trip` | `shipment_post`).
- Если `/me` вдруг недоступен/устарел — клиент теперь **не выдумывает** новую
  цифру: он скрывает строку «Yeni limit» (показывает лишь «+N elan» из заказа) и
  репортит `quota_me_refetch_failed` в телеметрию. Так что зачисление на бэкенде
  всё равно должно случиться независимо от `/me`.

## Что уже сделано на клиенте (контекст, менять контракт не нужно)

- **iOS: плитка «Bank kartı» для лимита убрана.** Причина — Apple guideline
  3.1.1 (оплата цифровой фичи картой мимо App Store = риск реджекта), плюс
  карта для лимита на бэкенде всё равно 422. На iOS лимит оплачивается только
  через App Store (IAP). Если стор-продукт не резолвится — показываем «üsul
  hazırda əlçatan deyil», а не мёртвую карту.
- **Экран успеха больше не выдумывает лимит** — «N → M» показывается только если
  `/me` подтвердил новое значение.
- **Ошибка `/me` больше не глотается** — уходит non-fatal в телеметрию
  (`quota_me_refetch_failed`).

Контракты `/listing-quota/orders`, `.../pay`, `/me` клиент **не менял**.

## Addendum (2026-09-22) — клиент финализировал сценарий, контракт не менялся

Сборка 37. Клиентский сценарий покупки лимита выровнен со сценарием VIP/Boost.
**Контракты `/listing-quota/orders`, `.../pay`, `/me` не изменились** — это только
про порядок вызовов и на что клиент теперь опирается:

- **Стор-покупка теперь запускается прямо с экрана подтверждения.** Нативный лист
  App Store / Google Play открывается **над** листом подтверждения, а не над
  спиннером «платёж обрабатывается». Отмена в сторе просто возвращает на лист (без
  ложного экрана ошибки); незавершённая транзакция закрывается в клиенте, поэтому
  повтор не упирается в `storekit_duplicate_product_object`.
- **Роутинг чека жёстко зафиксирован тестом.** Чек продукта `wawat.app.quota.*`
  уходит только на `POST /listing-quota/orders/{id}/pay`; VIP/Boost — на
  `/promotions/{id}/pay`. (Именно перепутанный роут раньше давал вечный спиннер:
  quota-чек уходил на `/promotions/{id}` → 404.)
- **Единственное жёсткое требование к вам:** ответ `/pay` = **HTTP 200 +
  `data.status:"paid"` синхронно, с уже зачисленным лимитом.** Сразу после `/pay`
  клиент дёргает `/me` и ведёт на экран успеха. Если зачисление «догоняет» после
  ответа `/pay`, `/me` вернёт старый лимит и пользователь не увидит рост (деньги
  при этом списаны). Отложенного/eventual зачисления у лимита быть не должно.
- **Свежий лимит клиент читает прямо из ответа `/me`** (без гонок с локальным
  кешем): `GET /me` не должен отдавать закешированный `listing_quota` после `/pay`.
- Пункт 1 (карта A/B) по-прежнему **открытый блокер** оплаты картой — ждём ответа.
